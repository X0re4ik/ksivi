# 🧭 Дорожная карта: путь от нуля до робототехнической системы на ROS 2

> Цель каждого урока — получить **одно маленькое понимание**, подкреплённое командой на живом роботе.
> Чекпоинт — вопрос себе: «Могу ли объяснить это своими словами?»

Общий секрет: робототехническая система на ROS = **граф узлов (nodes), обменивающихся данными через топики (topics)**.
Всё остальное — частные случаи этого графа.

---

## Урок 1. Карта мира ROS: узлы и топики
**Понимание:** ROS-система — это много независимых программ (узлов), которые общаются «трубами» (топиками).
**Команды:** `ros2 node list`, `ros2 topic list`, `ros2 topic info <тема>`
**Чекпоинт:** Кто публикует данные лидара? Кто слушает команды движения?

## Урок 2. Данные изнутри: что реально летит по трубам
**Понимание:** У каждого топика есть формат сообщения (msg). Лидар = массив расстояний. Команда движения = линейная скорость + угловая.
**Команды:** `ros2 topic echo /cmd_vel`, `ros2 topic type /scan`, `ros2 interface show sensor_msgs/msg/LaserScan`
**Чекпоинт:** Что означают числа в сообщении LaserScan?

## Урок 3. Рулевое управление своими руками
**Понимание:**cmd_vel — «дроссель» робота: одно число — вперёд/назад, другое — влево/вправо. Дифф-привод: крутить колёса с разной скоростью.
**Команды:** `ros2 run teleop_twist_keyboard ...`, публикация Twist из Python
**Чекпоинт:** Как естественным образом заставить робота описать круг?

## Урок 4. Скелет робота (TF): «где у робота что»
**Понимание:** TF — дерево координатных систем. odom→base_footprint→колёса. Сенсор знает позу, привязанную к данным.
**Команды:** `ros2 run tf2_tools view_frames` (смотрим PDF-граф), `ros2 tf2_echo odom base_footprint`
**Чекпоинт:** Почему нельзя «захардкодить» координаты, а нужен TF на лету?

## Урок 5. Анкета робота (URDF): описание из XML
**Понимание:** URDF/xacro — XML-файл, где описаны все звенья (links) и соединения (joints). Именно из него Gazebo строит физическую модель, а RViz рисует.
**Команды:** открыть `robolaunch_cloudy_description/urdf/diffbot_system.urdf.xacro`; поменять `wheel_diameter` в конфиге, пересобрать, посмотреть эффект
**Чекпоинт:** Что произойдёт, если сделать колёса в два раза толще?

## Урок 6. Сердце системы: ros2_control и «кто крутит моторы»
**Понимание:** В железе `cmd_vel → регулятор → PWM → мотор` делает связка `ros2_control` + драйвер `diffbot_system` + прошивка ESP32. В симуляции то же самое делает плагин Gazebo diff_drive.
**Команды:** чтение `gazebo_control.xacro` и `diffbot_system.cpp`; сопоставление — где что
**Чекпоинт:** Какой файл придётся трогать, если колёса будут не 2, а 4?

## Урок 7. Глаза робота вживую
**Понимание:** Датчики — это просто узлы-издатели. Их данные надо *видеть*, чтобы использовать.
**Команды:** RViz c роботом: RobotModel + LaserScan + Camera + TF
**Чекпоинт:** При повороте робота кадр камеры «чинится», потому что...

## Урок 8. SLAM: карта из движения
**Понимание:** SLAM = «оценка своей позы (TF) + накопление наблюдений (лидар) = карта».
**Команды:** `sim_slam.launch.py`, teleop, RViz: смотреть, как растёт карта
**Чекпоинт:** Почему карта дёргается, если ехать быстро и резко?

## Урок 9. Навигация (Nav2): «доехать сам до точки»
**Понимание:** Nav2 использует карту + локализацию, чтобы строить путь (global plan) и исполнить его (local plan, обходя препятствия вживую).
**Команды:** `sim_nav.launch.py`, цель в RViz кнопкой «2D Goal Pose»
**Чекпоинт:** Чем глобальный план отличается от локального?

## Урок 10. Свой узел: пишем код на Python
**Понимание:** Всё, что раньше было «готовым софтом», теперь пишем сами — тот же API: узел, подписка, публикация.
**Команды:** Python-нода «движение по квадрату»: читать odometry, публиковать cmd_vel
**Чекпоинт:** Почему движение «по квадрату» дрейфует, как поправить?

## Урок 11. Launch-файлы: собираем систему одним файлом
**Понимание:** Launch = скрипт, поднимающий множество узлов сразу. Систему запускать одним словом.
**Команды:** писать свой `<имя>.launch.py`, стартующий sim + RViz + слам
**Чекпоинт:** Какой апельсин (argument) добавить, чтобы запускать с другим миром?

## Урок 12. Мост в реальность (когда появится железо)
**Понимание:** Архитектура не меняется: ESP32-прошивка = один узел на micro-ROS, питание вам не нужно искать отдельно. Например: на реальном роботе узел-драйвер — тот же `diffbot_system`, но поверх serial.
**Команды:** прошивка `firmware.ino` → `micro_ros_agent` → тот же `diffbot_system.launch.py`
**Чекпоинт:** Почему в этом же workspace и на реального робота скрипты те же?
